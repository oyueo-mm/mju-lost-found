# MJU Find 기관 담당자·통계 체계 개편 결과

검증일: 2026-11-02 KST. Production 배포·마이그레이션·데이터·환경변수는 변경하지 않았다.

## A. 기존 구조 분석

- Next.js 16.3.4 App Router, NextAuth Google/JWT 인증, Prisma 7/PostgreSQL 구조를 유지했다.
- 서비스 관리자 권한은 기존 `User.isAdmin`을 유지한다. 조직의 LEADER/ADMIN/MEMBER는 조직 업무 권한이며 물품 관리 권한으로 승격하지 않는다.
- 기존 외부 이용 승인 `ExternalAccessGrant`는 로그인 허용에 사용한다. 이전의 명시적 `canManageItems`만 가입된 계정의 기관 담당 권한으로 이전하며, 일반 외부 승인에는 물품 관리 권한을 주지 않는다.
- 기존 Organization, FoundPost/LostPost, custody JSON, PostStatusChange, Notification, /admin/stats, MetricDaily, ActivityDay를 재사용했다. 별도 기관 마스터나 통계 수집 시스템을 만들지 않았다.
- 이전 보관 정보·알림·KST 기간 계산 및 등록 폼/홈 문구 변경도 유지했다. AI·이미지 검색 엔진은 이번 UI 변경으로 수정하지 않았다.

## B. 역할 및 권한

| 주체 | 허용 범위 |
|---|---|
| 일반 회원 | 기존 본인 글 등록·수정·완료. 타인 물품 관리 불가 |
| 기관 담당자 | 실제 접수 전 공개 습득물 조회·접수 확인, 소속 기관 물품의 장소 변경·반환·인계, 관련 이력 조회 |
| 서비스 관리자 | 기존 전체 관리 권한, 담당자 지정·수정·회수, 전체 기관 조회, 사유를 남기는 기관 정정·완료 복구·접수 해제 |

- `/admin/institution-officers`: 이메일·닉네임으로 가입 계정을 검색하고 계정 식별 정보를 확인한 후 기관·시설·활성 여부·메모·변경 사유를 저장한다. 기관/캠퍼스 필터와 권한 변경 이력을 제공한다.
- 기존 조직을 관리 기관으로 지정하거나 새 Organization을 등록할 수 있다. 이미 지정된 기관의 캠퍼스를 바꾸는 대신 별도 기관을 등록한다.
- 담당자 지정은 isAdmin을 변경하지 않는다. 외부 승인·조직 관리자 역할만으로는 담당자 기능을 사용할 수 없다.
- DB에서 최신 계정·정지·탈퇴·담당자·기관 상태를 확인한다. 로그인된 JWT가 있어도 회수 후 다음 요청은 차단된다. 권한 회수와 물품 처리는 같은 계정 행 잠금으로 직렬화한다.
- 마지막 담당자가 해제되거나 다른 기관으로 옮겨도 물품은 원 기관에 남는다. 남은 활성 담당자와 보관 물품을 확인해 서비스 관리자에게 경고한다.
- 이중 역할은 서비스 관리자 권한 및 통계 분류가 우선한다. 이벤트를 두 역할에 중복 집계하지 않는다.

## C. 물품 관리·DB·API

- 발견 캠퍼스가 아닌 **실제 수령 기관 ID**가 관리 범위다. 발견 캠퍼스와 다른 캠퍼스 기관도 실제 수령을 확인하면 접수할 수 있다.
- 작성자 정보: 직접 보관 / 전달 예정 / 기관 전달 신고 / 위치 모름 / 미보관. 작성자 신고만으로 관리자 확인이 생기지 않는다. 직접 보관 시 상세 개인 위치를 요구하지 않는다.
- 기관 접수는 실제 보관 장소와 실물 확인 체크가 필요하다. 접수 후 작성자가 보관 정보나 캠퍼스를 바꾸어 확인 상태를 유지·위조할 수 없다. 본문·사진 등 기존 작성자 편집 권한은 유지한다.
- 반환은 기존 found COMPLETED / lost FOUND 체계와 연결한다. 기관 담당자는 본인 기관의 접수된 습득물만 반환 처리하며, 분실 글의 관리 처리는 서비스 관리자에게 한정한다. 작성자의 기존 본인 완료 기능은 유지한다.
- A 기관 인계 요청 → A가 계속 관리 → B가 실제 수령·보관 장소 확인 → B로 관리 기관 변경. 요청 중 반환은 차단하고 취소는 기존 기관에서 할 수 있다.
- 서비스 관리자의 잘못된 기관 정정·완료 복구·접수 해제에는 사유가 필수다. 완료 복구는 기존 기관을 유지한다. 접수 해제는 위치를 ‘모름’으로 바꾸며 이전 장소는 감사 로그에 보존한다.
- 상태 변경은 게시글 행 잠금과 expectedUpdatedAt 검사로 중복·충돌을 차단한다. 변경·이력·작성자 알림을 같은 트랜잭션에 기록하며 알림은 고유 처리 이력에 연결한다.
- 기관 담당자에게 타인 본문·사진 수정, 삭제, 서비스 관리자 페이지 접근 권한을 부여하지 않는다.

추가 스키마:

- `InstitutionOfficer`, `InstitutionOfficerAudit`.
- `Organization.managementCampus`.
- `FoundPost.custodyOrganizationId`, `pendingTransferOrganizationId` 및 조회 인덱스.
- `PostStatusChange.reason`, `organizationId`, `targetOrganizationId`.
- 이벤트/가입/방문/활동일의 `activityRole`, `activityOrganizationId`; 기존 activityAudience 유지.
- 역할 판정·스냅샷 보존 DB 함수, ActivityDay 스냅샷 보호 트리거, OperationalMetricDaily 뷰 확장.

API는 기존 `PATCH /api/posts/:id?type=found|lost`의 management 요청을 확장했다. 동작: confirm/location/complete/reopen/transfer_request/transfer_accept/transfer_cancel/correct_institution/release. 일반 편집과 별도 스키마·서버 권한으로 검증한다. 담당자·기관 등록은 requireAdmin을 확인하는 Server Action이다.

기관 담당자 관련 Preview 적용 마이그레이션:

1. `20261109000000_institution_officers`
2. `20261109010000_preserve_activity_day_role`
3. `20261109020000_lock_activity_day_snapshot`

두 후속 마이그레이션은 사용자 ID가 없는 ActivityDay의 서버 역할을 보존하고 UPDATE로 재분류하지 못하도록 보강한다. 기존 행을 일괄 갱신하거나 삭제하지 않는다. 기존 확인 장소가 기관명·캠퍼스에 정확히 대응할 때만 기관 ID를 연결하며, 대응 불명확한 확인 건은 서비스 관리자 정정 대상으로 남긴다.

## D. 통계

- 일반 운영/사용자 행동 지표는 이벤트 당시 member로 확인된 가입·등록·완료·메시지·활동을 사용한다. 관리자가 일반 회원 글을 처리해도 글의 member 등록 스냅샷은 바뀌지 않고 처리 이벤트만 관리자 실적에 들어간다.
- 현재 일반 계정 재고는 현재 역할로 계산한다. 과거 가입/행동은 저장된 발생 시점 분류로 계산한다. 담당자 지정·회수로 과거 가입·글을 재분류하지 않는다.
- 관리자 탭에 서비스 관리자/기관 담당자/전체, 기관·캠퍼스·담당자 필터를 추가했다. 방문·페이지뷰·검색·등록 및 접수·인계·반환·복구 실적과 기존 감사 이력을 함께 제공한다. 전체 개별 활동 열람은 서비스 관리자에게 한정된다.
- 카운터는 `audience_v3` 아래 역할·기관 차원을 기록한다. 개별 방문·검색의 사용자 ID는 수집하지 않는다. 담당자 필터에서는 수집할 수 없는 개인 트래픽 수치를 숨기고 처리·등록 기록만 표시한다.
- 방문은 기존 브라우저의 30분 비활동 세션 기준을 유지하며 시작 세션을 한 번 센다. 인증 상태는 수집 시점에 판정한다. 관리자 로그인 전 익명 방문은 신원 미확인 트래픽으로 구분하고 일반 회원 이용이라고 확정하지 않는다. 과거 익명 방문을 현재 계정으로 역추적하지 않는다.
- ActivityDay는 KST 날짜+익명 식별자당 첫 활동 역할을 유지한다. 같은 날 역할이 바뀌어도 활동일을 양쪽에 중복 생성하지 않는다. 역할별 시작 세션/활동일의 합을 사람 기준 전 기간 순사용자 수로 간주하면 안 된다. 다기기 통합 순방문자 추적은 제공하지 않는다.
- v2의 확인 가능한 member/anon 카운터는 유지한다. 세부 역할이 없는 과거 내부 카운터는 legacy로 남기며 서비스/기관 담당자로 임의 배분하지 않는다. 예전 서비스 관리자 전용 처리 테이블은 그 당시 수행 권한이 확인되는 감사 기록으로만 표시한다.
- 세부 역할 수집 시작은 DB의 `meta.since.institution_roles`를 표시한다. 시작 전 활동일·방문은 미측정이고 시작일은 부분 측정이다. 역할이 없는 과거 이벤트를 현재 역할로 덮어쓰지 않는다.
- 트래픽은 당시 소속 기관, 물품 처리 실적은 처리한 기관을 기준으로 필터한다. 서비스 관리자가 기관 물품을 대신 처리한 건도 처리 기관의 실적에 포함된다.
- 서버 요청량·지연·용량/Vercel 과금 등 인프라 지표는 전체 요청 기준을 유지했다.
- 오늘/사용자 지정/올해는 유지한다. 기존 week/month URL은 최근 7/30일로 해석한다. 오늘 포함 이전 6/29일이며 KST 시작일 00:00 이상, 종료일 다음 날 00:00 미만으로 조회한다. 예: 2026-11-02 → 10-27~11-02 / 10-04~11-02. 카드·그래프·기존 CSV/XLSX 내보내기는 같은 기간 해석을 사용한다. 기존에 없던 관리자 전용 내보내기는 추가하지 않았다.

## E. UI

- 기존 관리자 대시보드에 기관 담당자 관리·물품 관리 진입점을 추가했다. Header의 물품 관리는 최신 권한을 가진 계정에 표시한다.
- `/items`: 기관 보관/반환 완료/인계 요청/수령 대기/접수 전 공개 습득물을 구분한다. 검색·장소 필터·등록/접수 정렬·페이지 이동·처리 이력을 제공한다. 담당자는 자기 기관 범위, 서비스 관리자는 기관 선택이 가능하다.
- 게시글 상세의 기존 디자인 안에 접수·반환 관리 폼을 통합했다. 처리 유형과 복구 사유를 사람이 읽을 수 있게 표시한다.
- 1280px/390px에서 담당자 관리·물품 관리 화면을 브라우저 캡처하고 페이지 가로 넘침이 없음을 검증했다. 긴 기관명이 모바일 선택란을 넘치던 신규 문제를 수정했다.
- 신규 분실/습득 등록은 기타 기본값, 수동 선택 유지, 수정 시 저장된 카테고리 유지. 기존 데이터는 변경하지 않는다. 홈 검색 설명의 AI 용어는 7개 언어에서 제거하고 기존 스타일·의도된 줄바꿈은 유지했다.

## F. 테스트·증거

- 전체 Vitest: **205개 파일, 2,405개 테스트 통과**. TypeScript, ESLint 및 Vercel 최적화 빌드 통과.
- 신규/수정 테스트: 기관 권한 지정·회수와 비승격, 정지·탈퇴 차단, 외부 승인/조직 권한과 분리, 발견 캠퍼스와 실제 기관의 분리, 동시 처리/오래된 요청, 양방향 인계, 서비스 관리자 복구, 역할 우선순위, 일반/관리 통계·역할 수집 경계, KST 기간, 카테고리 기본값과 번역 문구.
- 고정 Preview의 브라우저/HTTP 검증 **16개 묶음 통과**, pageErrors 없음. 권한 없는 관리 API 403, 동시 접수 200/409, 최신 시각 충돌 409, 본문/삭제 차단, 실제 담당자 지정·회수 UI, Server Action 위조로 승격 불가, 기관 대시보드·통계 필터, 양방향 인계·반환·복구를 검증했다.
- 추가 브라우저 검증: 양쪽 등록 폼의 기타 기본값·수동 선택 유지, 수정 시 phone 복원, 작성자 신고가 미확인으로 유지, 작성자 본인 완료, 서비스 관리자 사유 기반 기관 정정·접수 해제, 홈 문구와 모바일 너비.
- 최신 배포의 모바일 상세 화면에서 인계 요청 중 기본 동작이 장소 변경인지 확인하고, 수령 기관의 실제 폼 버튼으로 인계 수령·반환을 완료했다. 처리 후 DB/API의 담당 기관·완료 상태도 일치했다.
- DB 실측: 담당자 생성 글 officer, 이중 역할 글 service, 회수 후 글 member, 지정 전 가입 member 유지. 가상 기관의 실제 방문 비콘이 officer/service 차원으로 나뉘어 저장됨을 확인했다. 활동일 역할 보존·UPDATE 불변성은 실제 DB 트랜잭션으로 확인하고 롤백했다.
- 기존 기능은 Preview에서 자연어 검색·이미지 추론·추천 조회·채팅 생성/메시지·알림의 성공 응답을 확인했다. 추천 품질, 실제 자동 매칭 작업 전체, 실시간 다중 접속 채팅 및 모든 기기/언어 조합을 실물 시나리오로 검증한 것은 아니다. 단위·회귀 테스트 통과와 구분한다.
- Google OAuth 시작 URL의 redirect_uri가 고정 Preview의 `/api/auth/callback/google`임을 확인했다. **실제 Google 계정 인증 완료 후 Preview 주소 유지 여부는 사용자 확인 대기 중**이다. 가상 JWT 세션은 Google 인증 완료 검증을 대체하지 않는다.

## H. 남은 확인과 Production 적용 준비

- 실제 기관별 협력 여부·물품 수령 가능 시간·담당 시설·담당자 계정 소유자를 기관과 확인해야 한다. 새 기관 등록이 공식 제휴를 의미하지 않는다. 실제 주인 확인·실물 반환 판단은 담당자의 업무 절차로 정해야 한다.
- 기존 기관명/캠퍼스가 정확히 연결되지 않은 관리자 확인 건은 서비스 관리자가 확인하고 정정해야 한다. 역할이 기록되지 않은 과거 활동은 복원할 수 없으며 재분류하지 않았다.
- 담당자 목록/계정 검색은 100/20건, 최근 권한 감사 이력은 30건, 상세 물품 이력은 50건으로 제한한다. 대규모 기관 도입 시 추가 페이지 이동/장기 감사 조회를 검토한다.
- 현재 한 계정당 한 기관 담당 지정을 제공한다. 여러 기관 동시 담당이나 시설별 별도 권한은 구현하지 않았다. 시설은 담당 안내이며 권한 경계는 기관 ID다.
- 관리자별 방문·검색 상세 및 관리자 전용 CSV/XLSX는 제공하지 않는다. 기존 운영/사용자 내보내기는 유지한다.
- 실제 Google 로그인 완료/복귀 결과는 별도 확인이 필요하다. 이미지 업로드·실물 자동 매칭 정확도와 실제 기관 반환 절차 전체는 이번 가상 데이터 검증 범위 밖이다.
- Production 적용 전: 변경 스키마·권한 이전 대상·정확히 연결할 기관·역할 수집 시작일 영향을 검토하고 DB 백업/PITR와 복구 연습을 확인해야 한다. **Production 백업은 이번 작업에서 실행하거나 확인하지 않았다.** 명시적 승인 후에만 마이그레이션과 배포를 진행한다.
- 롤백: 추가 테이블/컬럼과 감사 기록은 삭제하지 않는다. 호환되는 이전 앱으로만 전환하며, 기관 권한·진행 중 인계 데이터가 이미 생긴 뒤에는 구형 외부 승인 기반 권한 코드로 무조건 되돌리지 않는다. 필요 시 담당자 작업을 일시 중지하고 호환 수정본을 배포한다. 데이터 복구가 필요하면 별도 승인·검증된 백업 절차를 사용한다. 이전 SQL 함수/뷰 복원은 해당 앱 버전과 함께 검토해야 한다.
- 이번 변경 중 발견·해결: 긴 기관명 모바일 넘침, 인계 요청 중 상세 폼 기본 동작 불일치, 역할 수집 이전 활동의 측정 표시, ActivityDay 스냅샷 DB 보호 누락. CLI 배포 1차 인증 실패는 로그인 확인 후 명시적 팀 범위 재시도로 해결했다. 실제 Google OAuth 완료는 환경/계정 소유자 확인에 남아 있다.
