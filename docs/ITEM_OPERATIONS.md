# MJU Find 물품 운영 개선 보고서

> 이전 단계의 구현 기록입니다. 이후 도입한 독립 기관 담당자 권한·기관 간 인계·세부 역할 통계와 최신 Preview 검증 결과는 [기관 담당자 개편 보고서](INSTITUTION_OFFICER_REPORT.md)를 기준으로 확인하세요.

## 1. 기존 구조 분석

- Next.js 16.3.4 App Router, NextAuth JWT, Prisma 7 + Supabase PostgreSQL.
- 전체 관리자 권한은 `User.isAdmin` 하나이며 별도 최고 관리자 enum은 없다. 단체의 `LEADER/ADMIN/MEMBER`는 독립적인 단체 내부 역할이다.
- 외부 계정 승인은 `ExternalAccessGrant`의 이메일·소속·캠퍼스·활성 상태를 사용한다. 승인만 받은 외부 계정에는 원래 관리 권한이 없다.
- 분실물 `SEARCHING/FOUND`, 습득물 `KEEPING/COMPLETED`를 검색·AI·기존 상세 UI가 공유한다. `PostStatusChange`와 작성자 수정 경로, 알림 고유 제약을 재사용했다.
- 운영 통계는 원본 테이블, `MetricDaily`, `ActivityDay`를 조합했다. 기존에는 일부 방문·검색만 `isAdmin`으로 분리되었고, 전체 검색·가입·게시글·활성 집계와 현재 역할에 의한 과거 재분류 문제가 있었다.

## 2. 구현 기능

- 기존 외부 관계자 관리 화면에서 물품 담당 권한을 별도 지정·수정·회수한다. 학교 계정도 물품 담당자로 지정할 수 있다. 외부 승인 자체를 물품 담당 권한으로 승격하지 않는다.
- 담당자와 전체 관리자는 게시글 상세에서 접수 확인, 실제 보관 장소 변경, 완료 처리를 한다. 전체 관리자는 완료를 복구할 수 있다.
- 습득물 등록·수정에 직접 보관, 기관 전달 예정, 기관 전달 신고, 위치 모름, 미보관을 추가했다. 임시저장도 보관 정보를 보존한다.
- 일반 운영 통계와 관리자 활동 통계를 기존 탭 안에서 구분한다. 관리자 탭에는 서비스 이용량과 담당자·기관별 처리 실적을 추가하고 기존 상세 활동 화면도 유지했다.

## 3. DB·API 변경

추가형 마이그레이션:

1. `20261108000000_item_operations`: 습득물 `custody` JSON, 외부 승인 `can_manage_items`, 처리 이력의 작업·기관·이전/이후 보관 정보, 관련 알림 유형, 이벤트 시점 분류 컬럼과 불변 분류 트리거.
2. `20261108010000_classified_metric_counters`: 새 카운터 namespace와 `OperationalMetricDaily` 읽기 전용 뷰. 이전 카운터는 원본에 그대로 남는다.

기존 `PATCH /api/posts/[id]?type=found|lost`에 `{ management: { action, expectedUpdatedAt, confirmed: true, place? } }`를 추가했다. 관리 작업에 본문·사진 등 다른 항목을 혼합하면 거절한다. 작성자용 수정·삭제 API의 소유권 검증은 유지한다.

행 잠금, 현재 DB 권한 재확인, 수정 시각 비교, 상태 검증, 게시글 변경·감사 로그·알림의 단일 트랜잭션을 적용한다. 반복 알림은 게시글이 아닌 개별 처리 이력을 참조하여 기존 알림 고유 제약과 충돌하지 않는다.

## 4. 권한 차이

| 주체 | 허용 범위 |
| --- | --- |
| 일반 사용자 | 본인 글 수정·완료·삭제, 보관 정보 수정. 타인 관리 불가. 관리자 확인 정보 입력 불가 |
| 물품 담당자 | 지정 캠퍼스(또는 양쪽)에서 실제 접수·반환을 확인한 물품 관리. 다른 기관이 확인한 물품 변경 불가. 본문·사진·작성자 수정 및 타인 글 삭제 불가 |
| 전체 관리자 | 기존 전체 관리 권한 유지, 담당자 지정·회수, 캠퍼스·기관 제한 없이 상태 관리, 완료 복구 |

기관별 배정 테이블을 새로 만들지 않았다. 접수 확인 시 담당자의 승인된 소속을 보관 정보에 기록한다. 미확인 물품은 캠퍼스 안에서 실제 접수 확인을 명시한 담당자가 인수할 수 있다. 확인 후에는 같은 소속만 처리하며 기관 간 이전은 전체 관리자가 조정한다. 단체 내부 관리자 역할만으로 타인 물품 처리 권한을 주지는 않는다.

개별 관리자 통계 전체 조회는 기존 `ADMIN_ACTIVITY_VIEWER_IDS` 제한을 유지한다. 다른 전체 관리자는 본인 처리 실적만 본다. 공개 게시글 응답에는 확인 담당자 ID와 통계 역할 분류를 노출하지 않는다.

## 5. 보관·완료 처리

- 전달 예정은 직접 보관하면서 앞으로 전달할 계획이다. 접수 확인으로 표시하지 않는다.
- 기관에 전달했다는 작성자 입력은 신고이며 관리자 미확인으로 표시한다.
- 담당자가 실제 수령을 확인해야 기관 보관 확인이 성립한다. 담당자의 실제 확인 체크가 필수다.
- 습득물은 담당 기관의 접수 확인 후 반환 완료가 가능하다. 분실물은 찾음 확인 후 기존 `FOUND` 상태가 된다.
- 기존 작성자의 완료 처리 기능을 유지한다. 보관 확인과 작성자의 반환 완료 표시는 별도다.
- 작성자가 보관 정보 또는 캠퍼스를 변경하면 관리자 확인은 해제되고 변경 이력이 남는다. 기존 글의 보관 정보는 미등록으로 표시한다.
- 잘못된 완료는 전체 관리자가 복구한다. 원래 이력은 삭제하지 않는다.

## 6. 통계 분류와 이전 데이터

- `isAdmin`, 물품 관리 승인 계정, 활성 단체의 `LEADER/ADMIN`, 테스트 외부 계정을 관리 활동으로 분류한다. 관리 권한 없는 외부 승인 계정과 단체 일반 구성원은 일반 활동이다.
- 가입·분실/습득물 등록·대화 생성·메시지·완료 이력에는 DB 트리거가 발생 당시 분류를 기록한다. 갱신으로 과거 분류를 덮어쓸 수 없다. 활동 일자도 수집 시점 분류를 저장한다.
- 작성자와 처리자를 구분한다. 일반 회원이 등록한 물품을 담당자가 완료해도 등록 실적은 일반 회원에 남으며 처리 실적만 관리 활동이다.
- 일반 운영 요약의 검색·추천은 인증된 일반 회원 기준이다. 익명 방문·검색은 신원을 확인할 수 없으므로 별도 분류이며 일반 회원이라고 확정하지 않는다. 이미 관리자로 식별한 브라우저의 기존 통계 제외 설정도 유지한다.
- 세션은 브라우저의 기존 30분/날짜 경계 기준으로 한 번 시작하며 시작 당시 분류에 귀속한다. 로그인 도중 전환만으로 세션을 새로 만들지 않는다. 이후 페이지뷰는 수신 시점 인증 상태로 분리한다. 인증된 활동 일자 키는 1인·1일 하나이며 최초 기록 분류를 유지한다. 서로 다른 역할의 숫자를 합쳐 전역 순사용자로 표시하지 않는다.
- 검색 중복 제거는 역할과 계정별 메모리 HMAC 범위에서 수행한다. 다른 관리자의 같은 검색이 일반 회원 검색을 지우지 않는다.
- 이전 이벤트의 NULL 분류를 추정하거나 현재 역할로 역산하지 않는다. 이전 집계도 보존하되 새 역할 기준 카운터와 섞지 않는다. 화면·내보내기에 한계를 설명하고 수집 전 구간은 미측정/부분 측정으로 구분한다.
- Vercel 사용량, DB 용량, API/AI 응답 시간과 요청량은 실제 전체 부하 기준을 유지한다.

익명 방문자가 이후 관리자였음이 드러나도 이미 저장된 집계에는 개인 식별 연결 정보가 없어 과거 익명 방문을 소급 분류할 수 없다. 현재 구조에서 수집을 늘려 추적하지 않았다. 원본 게시글 삭제 후 등록 집계가 감소하는 기존 방식, 활동 기록의 기존 보유기간, 네트워크 재전송 시 방문 집계의 제한도 유지한다.

## 7. 기간 계산

`week`와 `month` URL 값은 호환성을 위해 유지하되 실제 의미를 최근 7일과 최근 30일로 바꿨다. KST 날짜의 오늘과 이전 6일/29일을 포함하고, DB에서는 KST 시작일 이상~마지막 날 다음 날 미만으로 조회한다. 저장된 UTC timestamp를 명시적으로 KST로 변환한다.

2026-11-02 기준 최근 7일은 10-27~11-02, 최근 30일은 10-04~11-02이다. 오늘·올해·사용자 지정과 내보내기, 일반·사용자·관리자 탭에서 같은 기간 해석을 공유한다. 관리자 상세 화면의 기존 `p=7` 공유 링크도 지원한다. 날짜·시간대 분석에 별도로 선택하는 기존 날짜 필터는 유지한다.

## 10. Production 영향·롤백·남은 검토

Production 배포 및 마이그레이션은 별도 명시적 승인이 필요하다. 데이터 삭제·실제 사용자 수정은 하지 않는다.

승인 후 적용 순서: 검증된 백업 확보 → 두 추가형 마이그레이션 → 새 앱 배포 → 상태 변경·알림·통계 점검. 새 카운터·NULL 분류로 인해 기존 기간 숫자가 줄거나 미측정으로 보이는 것은 의도된 분류 경계다. 신규 필드·기존 테이블 트리거로 INSERT/UPDATE 비용이 소량 증가하며 운영 규모에서 관찰이 필요하다.

문제가 생기면 직전 앱 버전으로 되돌리고 추가 필드·이력·뷰는 남겨 데이터를 보존한다. 이전 앱은 새 카운터 namespace를 기록하지 않으므로 롤백 기간의 분류되지 않은 집계를 새 통계에 억지로 합치지 않는다. 트리거 자체 문제가 확인될 때만 DB 담당자가 해당 트리거를 비활성화하고, 그 기간은 미측정으로 취급한다. 즉시 DROP COLUMN/테이블 삭제나 다운 마이그레이션은 하지 않는다.

실제 담당 기관 이름·수령 가능 여부·캠퍼스 지정은 운영자가 확정해야 한다. 기관 선택 예시는 공식 협력·수령 보장을 뜻하지 않는다. 기관명 표준화·기관 간 인계·다국어 신규 문구 번역·실제 모바일 조작과 OAuth 검증은 후속 운영 검토 대상으로 남는다.
