# 감사 쪽지와 기여도·랭킹 검토

작성 2026-11-03. 코드: `src/lib/thanks/`, `src/components/thanks/`, `src/app/(main)/me/thanks/`.
마이그레이션: `prisma/migrations/20261112000000_thank_note` (테이블 1개 추가, 기존 행 변경 없음).

## 1. 감사 쪽지

### 흐름 (2026-11-04 Production 출시)
1. 분실자와 습득자가 게시글의 1:1 채팅으로 연결된다.
2. **작성자가 채팅방에서 `찾음 완료`를 누르면** 그 방의 상대방이 반환 상대방으로 자동 기록된다
   (`PostReturn`, 상대방을 고르게 하지 않는다). 게시글 상세 화면에서 완료하면 반환 상대방이 확정되지 않으므로
   누구에게도 쪽지 작성 자격이 생기지 않는다(기존 완료 글도 같다).
3. 물건을 돌려받은 사람(분실물: 작성자, 습득물: 채팅 상대방)에게 채팅방 안에 "감사의 마음을 전해보세요" 카드가 보인다
   (`보내기` / `나중에`; 나중에는 한 줄로 접히고 이 기기에서 기억). 게시글 상세에서도 접힌 한 줄로 제공된다.
4. 받은 사람은 앱 내 알림(웹 푸시 아님)을 받고 `내 정보 > 받은 감사 쪽지`(/me/thanks)에서 본다. 기본은 나만 보기.
5. 받은 사람이 확인 후 공개하면 프로필에 **보낸 사람 없이** 본문과 공개일만 표시된다. 공개 철회·숨기기·신고가 가능하다.

### 자격 (`eligibility.ts`, 쓰기마다 서버가 DB로 다시 계산)
- 게시글이 완료 상태이고 **활성 `PostReturn`이 있다**(완료 취소 시 `revoked_at`으로 종료, 행은 보존).
- 발신자 = 그 반환의 `owner`(돌려받은 사람), 수신자 = 그 반환의 `finder`. 클라이언트는 게시글과 본문만 보낸다.
- 반환의 채팅방에서 **두 사람 모두 메시지를 보냈다**. 정지·탈퇴 계정, 자기 자신은 제외.
- 완료한 사람과 발신자는 같을 필요가 없다(습득물은 습득자가 완료하고, 분실자가 쪽지를 보낸다).
- 반환 연결 없이 쓰인 과거(Preview) 쪽지는 `return_id`가 NULL로 보존된다. 추측으로 연결하지 않는다.
  Production에는 이전 쪽지가 없다.

### 악용 방지
- 같은 게시글·같은 발신자 1회(DB unique, 동시 요청도 한 건만 저장 — 실제 DB 동시성 시험으로 확인).
- 본문 0~500자(태그 또는 메시지 필수), 자기 자신 금지(서비스 + DB CHECK). 하루 건수 제한은 2026-11-04에 없앴다
  (후기마다 실제 반환 기록 1건에 묶이고 게시글·발신자당 1건이라, 하루에 여러 물건을 돌려받으면 각각 보낼 수 있어야 한다).
- 같은 게시글에서 두 채팅방이 동시에 완료를 눌러도 활성 반환은 하나(부분 unique 인덱스 + 행 잠금).
- 연락처·이메일·학번·주민번호 형태·메신저 ID가 보이는 쪽지는 서버가 공개를 거부(휴리스틱, 완전하지 않음).
- 공개 후에도 받은 사람이 철회할 수 있고, 신고가 접수된 공개 쪽지는 관리자가 검토할 때까지 프로필에서 가려진다.

### 신고
기존 신고 체계를 재사용한다(`targetType = thank_note`). 받은 사람과, 공개된 쪽지에 한해 누구나 신고할 수 있고
(보낸 사람 본인 제외), 비공개 쪽지는 받은 사람만 신고할 수 있다. 사유 선택·상세 사유·중복 방지·관리자 알림은 기존과 같다.
관리자의 처리는 `감사 쪽지 숨김`(`admin_hidden_at`, 행 보존, 공개 해제) 또는 반려. 신고 즉시 삭제하지 않는다.

### 하지 않는 것 (의도적)
- **반환 검증 표시 없음.** 완료는 작성자 본인의 표시일 뿐이므로 "검증됨"/"반환 확인" 같은 문구를 쓰지 않는다.
- 점수·배지·랭킹과 연결하지 않는다(아래 2절). 휴대폰 웹 푸시도 보내지 않는다(앱 내 알림만).
- 기관 채팅방(기관 계정)은 쪽지 대상이 아니다. 기관 반환 정책이 정해지면 `PostReturn`을 확장한다.
- "숨기기"는 DB 삭제가 아니다(`hidden_at`, 되돌리기 없음). 화면 문구도 그렇게 적는다.

### 되돌리기
코드는 이전 배포로 되돌릴 수 있다. 단, 감사 쪽지 알림(`NotificationType.thank_note`)이 이미 생긴 뒤에는
이전 코드가 그 알림 유형을 모를 수 있으므로 되돌리기 전에 해당 알림 행을 확인한다. 스키마는 추가형이라 남겨 두어도 무해하다.

## 1-1. 감사 후기 칭찬 태그 (Phase 3-B)

### 상태
- **Preview DB 적용 완료(2026-11-04, `migrate deploy`). Production DB 미적용.** 적용 전 Preview 전체 백업
  `C:/Users/hihi9/mju-lost-found-backups/preview-2026-11-04-pre-thank-tags`(복원 검증·마이그레이션 리허설 통과).
- 마이그레이션 `prisma/migrations/20261120000000_thank_note_tags`(이름은 이 저장소의 순차 가상 날짜 관례, 마지막 적용분 `20261113…` 다음).
- Preview `_prisma_migrations`에는 이 브랜치에 없는 `20261102000000_identity_access_purpose`(다른 브랜치에서 과거 적용)가 있다. ThankNote와 무관.

### 스키마
- `tags TEXT[] NOT NULL DEFAULT '{}'`. 기존 행은 `{}`(태그를 지어내지 않음), 다른 값은 그대로.
- `ThankNote_body_check(1..500)` → `body_length_check(<=500)` + `content_check(본문에 공백 아닌 글자 OR 태그 1개 이상)`
  + `tags_check(다섯 코드만)` + `tags_unique_check(중복 금지, IMMUTABLE 함수 thank_note_tags_unique)`.
- 코드: `kind`, `quick_reply`, `kept_well`, `helpful`, `kept_promise` (표시 문구는 `thanks.tag.<code>`).

### 배포 순서와 되돌리기
- 태그 코드는 **마이그레이션 적용 후에만** 배포한다(Prisma가 `tags` 열을 조회). Production: 백업 → 마이그레이션 → 배포.
- 마이그레이션 뒤 이전 코드: 태그를 모르는 클라이언트는 열을 무시하고, 새 쪽지는 기본값 `{}` + 비어 있지 않은 본문이라 제약을 통과한다.
  태그만 있는 후기는 이전 화면에서 **본문이 빈 쪽지**로 보인다(태그는 안 보임) -- Preview 검증 결과는 Phase 3-B 보고서 참고.
- 스키마 되돌리기 SQL은 마이그레이션 머리말. 태그만 있는 후기가 0건일 때만 가능(지워야 하므로 하지 않는다).

## 2. 기여도·랭킹 (검토만, 구현하지 않음)

### 결론
지금은 공개 랭킹을 도입하지 않는다. 실제 반환을 확인할 수단이 없어 어떤 점수도 조작 가능하고,
Production 규모(게시글 78건, 그중 일반 사용자 11건)에서는 순위가 소수 계정의 활동만 비춘다.

### 점수 후보와 문제
| 신호 | 문제 |
|---|---|
| 게시글 수 | 허위·중복 등록으로 바로 부풀어진다(제외). |
| 완료 표시 수 | 작성자 본인이 누르는 값. 가짜 완료 가능. |
| 감사 쪽지 수 | 다중 계정·지인 간 담합으로 쌓을 수 있고, 쪽지를 요구하는 압박이 생긴다. |
| 기관 접수 확인(`custody.confirmedAt`) | 유일하게 제3자(담당 기관)가 확인한 값. 다만 기관 담당자 지정이 아직 0건. |

### 도입한다면 필요한 전제
1. 반환 확인: 기관 접수 확인, 또는 양쪽이 모두 "돌려받음/돌려줌"을 누르는 2자 확인.
2. 점수는 서로 다른 상대와의 확인된 반환만, 같은 상대 반복은 1회로, 기간당 상한.
3. 다중 계정 신호(같은 상대와만 반복, 가입 직후 반복 완료)는 점수에서 제외하고 관리자 검토 대상으로.
4. 공개 랭킹은 본인 선택(기본 비공개), 닉네임 외 정보 비노출, 순위 대신 "감사 받은 반환 n건" 같은 본인용 기록부터.
5. 감사 쪽지는 점수에 넣지 않거나, 넣더라도 확인된 반환에 연결된 것만.
