# 감사 쪽지와 기여도·랭킹 검토

작성 2026-11-03. 코드: `src/lib/thanks/`, `src/components/thanks/`, `src/app/(main)/me/thanks/`.
마이그레이션: `prisma/migrations/20261112000000_thank_note` (테이블 1개 추가, 기존 행 변경 없음).

## 1. 감사 쪽지

### 흐름
1. 분실자와 습득자가 게시글의 1:1 채팅으로 연결된다.
2. 작성자가 게시글을 완료로 표시한다(분실물 `찾음`, 습득물 `완료`).
3. 물건을 돌려받은 사람에게만 게시글 상세에 접힌 한 줄 "도와주신 분께 감사 쪽지 보내기 (선택)"이 보인다.
   쓰지 않아도 완료 처리에는 아무 영향이 없다.
4. 받은 사람은 `내 정보 > 받은 감사 쪽지`(/me/thanks)에서 확인한다. 기본은 나만 보기.
5. 받은 사람이 "프로필에 공개하기"를 누르고 확인하면 공개 프로필에 **보낸 사람 없이** 본문과 공개 날짜만 표시된다.
   언제든 비공개로 되돌리거나 목록에서 숨길 수 있다(숨기면 공개도 내려간다). 숨김은 DB 삭제가 아니라
   `hidden_at` 표시이며, 받은 사람의 목록·프로필에서 다시 보이지 않는다(되돌리기 기능은 없음).
   연락처·이메일·학번처럼 보이는 내용이 있는 쪽지는 서버가 공개를 거부한다(`looksPersonal`, 휴리스틱).

### 누가 누구에게 (`eligibility.ts`, 쓰기마다 서버에서 다시 계산)
| 게시글 | 보내는 사람 | 받는 사람 |
|---|---|---|
| 분실물 | 작성자(분실자) | 그 글로 채팅한 상대(습득자) |
| 습득물 | 그 글로 채팅한 상대(분실자) | 작성자(습득자) |

조건: 게시글 완료 표시 + 그 게시글의 1:1 채팅방에서 **두 사람 모두 메시지를 1개 이상** 보냄.
기관 채팅방, 자기 자신, 정지·탈퇴 계정은 제외.

### 악용 방지
- 같은 게시글·같은 발신자는 1회(DB unique `uq_thanknote_post_sender`, 동시 요청도 막힘).
- 발신자당 24시간 5건.
- 본문 1~500자(DB CHECK), 자기 자신에게 금지(DB CHECK).
- 클라이언트는 게시글·수신자·본문만 보낸다. 권한·관계는 모두 서버에서 DB로 다시 확인.
- 공개는 수신자만 가능. 공개 화면에는 발신자 정보가 없다.
- 작성 화면에 "이름·연락처·학번 같은 개인정보는 적지 마세요" 안내.

### 하지 않는 것 (의도적)
- **반환 검증 표시 없음.** 완료는 작성자 본인의 표시일 뿐이므로 "검증됨"/"반환 확인" 같은 문구를 쓰지 않는다.
  화면에는 "서비스가 반환 사실을 확인한 것은 아니에요"라고 적는다.
- 점수·배지·랭킹과 연결하지 않는다(아래 2절).
- 알림 없음: 새 알림 종류는 `NotificationType` enum 변경(추가 마이그레이션)이 필요해 이번 범위에서 뺐다.
- 신고 없음: 쪽지는 받은 사람에게만 보이고, 받은 사람이 지울 수 있어 1차 안전장치로 충분하다고 판단.
  공개 쪽지 신고가 필요해지면 `ReportTargetType`에 값을 추가해야 한다(마이그레이션).
- 다국어: 쪽지 화면 문구는 한국어만(메뉴 이름 `me.thankNotes`만 7개 언어). 보관 상태 화면과 같은 수준.

### 배포 순서
1. Preview DB에 마이그레이션 적용 → Preview 배포 → 테스트 계정 1, 2로 정상 흐름·악용 시나리오 확인.
2. Production: 백업 → `migrate deploy` → 배포. 마이그레이션 전에 코드가 먼저 나가도 상세·프로필은 쪽지 부분만 숨고
   (/me/thanks는 "불러오지 못했어요"), 다른 기능에는 영향이 없다.
3. 되돌리기: 코드 롤백만으로 충분(테이블은 남겨도 무해). 테이블까지 지우려면 `DROP TABLE "ThankNote";`
   후 `prisma migrate resolve --rolled-back 20261112000000_thank_note`.

## 2. 기여도·랭킹 (검토만, 구현하지 않음)

### 결론
지금은 공개 랭킹을 도입하지 않는다. 실제 반환을 확인할 수단이 없어 어떤 점수도 조작 가능하고,
Production 규모(게시글 78건, 그중 일반 사용자 11건)에서는 순위가 소수 계정의 활동만 비춘다.

### 점수 후보와 문제
| 신호 | 문제 |
|---|---|
| 게시글 수 | 허위·중복 등록으로 바로 부풀어진다(제외). |
| 완료 표시 수 | 작성자 본인이 누르는 값. 가짜 완료 가능. |
| 감사 쪽지 수 | 다중 계정·지인 간 담합으로 쌓을 수 있고, 쪽지를 요구하는 압박이 생긴다. |
| 기관 접수 확인(`custody.confirmedAt`) | 유일하게 제3자(담당 기관)가 확인한 값. 다만 기관 담당자 지정이 아직 0건. |

### 도입한다면 필요한 전제
1. 반환 확인: 기관 접수 확인, 또는 양쪽이 모두 "돌려받음/돌려줌"을 누르는 2자 확인.
2. 점수는 서로 다른 상대와의 확인된 반환만, 같은 상대 반복은 1회로, 기간당 상한.
3. 다중 계정 신호(같은 상대와만 반복, 가입 직후 반복 완료)는 점수에서 제외하고 관리자 검토 대상으로.
4. 공개 랭킹은 본인 선택(기본 비공개), 닉네임 외 정보 비노출, 순위 대신 "감사 받은 반환 n건" 같은 본인용 기록부터.
5. 감사 쪽지는 점수에 넣지 않거나, 넣더라도 확인된 반환에 연결된 것만.
