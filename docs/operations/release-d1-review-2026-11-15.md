## 요청 제한

기존 `RateLimitCounter`를 사용하며 모든 창의 원자적 UPSERT를 한 트랜잭션으로 묶었다. 초과 시 전체 롤백하므로 거절된 재시도가 일간 한도를 소모하지 않는다. 모든 인스턴스가 같은 Postgres 카운터를 공유한다. 한도 초과는 429, 카운터·트랜잭션·익명 해시 설정 장애는 503과 Retry-After 5초다. API가 아닌 Server Action은 프로토콜의 HTTP 상태를 바꾸지 않고 별도 장애 안내를 반환한다. 카운터 정리는 승인 판정 이후 독립된 예외 처리로 실행한다.

## 익명 식별

- 서버 환경 `VERCEL=1`일 때만 Vercel이 제공하는 단일 IP 헤더를 신뢰한다. 우선 `x-vercel-forwarded-for`, 없으면 `x-forwarded-for`; 유효하지 않은 값·다중 주소·zone ID·x-real-ip 단독은 신뢰하지 않는다.
- IPv6 동등 표기와 IPv4 매핑을 정규화한 뒤 AUTH_SECRET을 포함해 해시하며 원본 IP를 DB에 저장하지 않는다. Vercel 외 환경이나 식별 불가 요청은 공통 unknown 버킷으로 제한한다.
- 신뢰 근거: [Vercel Request Headers](https://vercel.com/docs/headers/request-headers)는 전달 IP 헤더를 플랫폼에서 덮어쓴다고 명시한다. 다른 프록시/호스팅으로 옮기면 신뢰 경계 재검토가 필요하다. 공유 NAT 및 IPv6 주소 회전은 사용자별 인증 제한과 별개로 남는 한계다.

사용자가 알려준 외부 scratchpad의 `audit/regress.mjs`와 과거 결과 파일을 찾았다. 앞선 ‘원본 미확인’ 기록은 당시 검색 범위에 관한 기록이며, 이제 원본을 근거로 검사 영역을 확인했다. 원본을 그대로 실행하지 않고 `scripts/regression/preview.mjs`로 재구성하고 같은 디렉터리 README에 실행·정리 방법을 정식 관리한다.

- 원본은 기존 계정 1·2·관리자 13을 사용하고 신원 설정과 알림 읽음을 변경하며, 실패해도 종료 코드 0이었다. 새 검사는 매번 독립 사용자 3개를 생성하고 로컬 서버 전용 임시 서명 키를 사용한다. Production DB/Storage는 가드로 거부하고 임의 서버 URL을 받지 않는다.
- 최종 **16/16 통과**: 인증, 게시글 생성·조회·삭제, 업로드·첨부, 임베딩 재계산, 네 검색 모드, 채팅 생성·메시지·Realtime, 채팅 사진·비참여자 차단, 알림 생성·읽음, 관리자 API·화면 및 일반 사용자 차단. 배포된 Preview와 같은 D-1 앱 코드의 로컬 빌드 + 실제 Preview DB/Storage에서 실행했다. 배포된 Preview UI의 사용자 수동 검증과 구분한다.
- 원본이 허용했던 로컬 이미지 검색 502를 허용하지 않고 실제 200을 확인했다. 원본의 삭제 상태 기록도 인증 Storage 목록의 삭제 전 존재/후 부재와 DB 행 부재 단정으로 보강했다.
- 새 검사 작성 중 알림 DTO의 소문자 유형 및 채팅 참조 필드 가정을 수정했다. Storage HEAD 부재 응답의 오류 표현도 확인하여 명확한 목록 조회로 검증했다. 최종 성공을 얻기 전에 실패한 실행도 있었으며 앱 기능 수정으로 해결한 것은 아니다.
- 최종 실행: 신규 사용자 365~367, 게시글 252, 방 160. 실패한 개발 실행 사용자 356~364, 게시글 249~251, 방 157~159도 정확한 소유권을 확인하고 모두 정리했다. 기존 사용자·시드·감사 기록은 삭제하지 않았다. 정리 실패에 대비해 로컬 .vercel에 비밀 없는 실행 명세를 기록하고 `--cleanup-run`으로 재검증 후 정리할 수 있다.
- 원본 사진이 Storage에서 삭제된 뒤에도 이전에 요청한 공개 CDN URL은 200이었다. Storage 원본과 DB 삭제를 통과 조건으로 삼고 CDN 응답은 별도 결과로 보존한다. 즉시 공개 캐시 회수까지 성공했다고 보고하지 않는다. D-1에서 캐시 정책을 바꾸지 않았다.
- Realtime 수신 성공은 기능 회귀 결과이며 공개 채널 인증 문제를 해결했다는 의미가 아니다. D-3 구현은 하지 않았다. 실제 Google OAuth 자동화는 하지 않았으며 사용자의 배포 Preview 수동 로그인 결과로 보완했다.
- 결과 요약: `docs/operations/release-d1-regression-2026-11-16.json`. 앱·스키마·배포는 변경하지 않았고 원격 Push 없음. 위 최초 33개 파일에 정식 검사·README·결과 파일 3개가 추가됐다.
- 최종 재조회: 이번 검사들의 사용자·게시글·방·메시지·알림 잔여 행 각각 0, 해당 8개 Storage 폴더 잔여 파일 0. 전체 단위 테스트도 254개 파일 2,931/2,931로 재통과했고 새 회귀 스크립트 린트 통과. D-1 자동·사용자 수동 검증을 마무리했다.

## 운영상 남은 한계

- fail-closed로 DB/풀 장애 때 정상 요청도 잠시 차단된다. 트랜잭션 대기 2초/실행 3초 제한을 두었으며 DB 왕복이 늘어난다. 위 실측은 소규모 Preview 비교이며 기관의 실제 브라우저 일괄 등록 부하 시험은 아니다.
- 고정 창 경계에서 두 창의 예산이 근접해 사용될 수 있다. 이는 슬라이딩 창/전역 비용 예산이 아니며 기능별 공유 계정·네트워크 악용을 전부 막지는 않는다.
- 감사 쪽지의 기존 저장 트랜잭션 안에서 별도 제한 트랜잭션을 사용하므로 짧게 두 연결이 필요할 수 있다. 제한 카운터는 이후 콘텐츠 저장이 실패해도 성공한 입장 시도를 계산한다.
- 새 DB 스키마가 없으므로 이전 Preview 배포로 재지정해 코드 롤백할 수 있다. 새 카운터 행은 구버전이 무시하며 신고 증거·백업은 그대로 보존한다.
