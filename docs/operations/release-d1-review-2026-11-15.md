## 요청 제한

기존 `RateLimitCounter`를 사용하며 모든 창의 원자적 UPSERT를 한 트랜잭션으로 묶었다. 초과 시 전체 롤백하므로 거절된 재시도가 일간 한도를 소모하지 않는다. 모든 인스턴스가 같은 Postgres 카운터를 공유한다. 한도 초과는 429, 카운터·트랜잭션·익명 해시 설정 장애는 503과 Retry-After 5초다. API가 아닌 Server Action은 프로토콜의 HTTP 상태를 바꾸지 않고 별도 장애 안내를 반환한다. 카운터 정리는 승인 판정 이후 독립된 예외 처리로 실행한다.

- 기존 고비용 수치는 바꾸지 않았다. Production 최근 30일 집계: AI 80건(평균 609.9ms), semantic 11건(718.9ms), 이미지 검색 4건(529.8ms), 업로드 52건(462.7ms). 표본이 작고 사용자별 비용 자료가 없어 새 최적 수치를 실증했다고 주장하지 않는다.

- Production 최근 30일 댓글·피드백·감사·키워드 생성은 각 0건. Preview 감사 쪽지 최대 2/분·5/일, 댓글 최대 1/분이었다. 새 한도는 자동 반복을 억제하는 초기 예산이며 실제 정상 사용량에 따른 최적값은 아니다. 감사는 기존 글/발신자 중복 제한과 일간 무제한 정책을 유지한다. 키워드는 최초 20개 설정을 허용하도록 분당 예산을 30으로 잡았다.

- 댓글 API, 피드백 Server Action과 정정 요청, 감사 Server Action, 키워드 Server Action의 모든 생성 호출은 해당 서비스로 수렴하며 직접 삽입하는 별도 생성 경로는 없음을 검색했다. 실패 시 생성·알림 전송을 하지 않는 서비스 테스트를 추가했다.
- 통합 검색은 기존 동작대로 AI 할당량 초과 시 추가 추론 없이 키워드 결과 200으로 폴백한다. 명시적 AI/semantic/image 검색은 429다. 통합 검색도 제한 시스템 장애는 503으로 전달한다. 기존 폴백 회귀 테스트를 보존했다.

## 익명 식별

- 서버 환경 `VERCEL=1`일 때만 Vercel이 제공하는 단일 IP 헤더를 신뢰한다. 우선 `x-vercel-forwarded-for`, 없으면 `x-forwarded-for`; 유효하지 않은 값·다중 주소·zone ID·x-real-ip 단독은 신뢰하지 않는다.
- IPv6 동등 표기와 IPv4 매핑을 정규화한 뒤 AUTH_SECRET을 포함해 해시하며 원본 IP를 DB에 저장하지 않는다. Vercel 외 환경이나 식별 불가 요청은 공통 unknown 버킷으로 제한한다.
- 신뢰 근거: [Vercel Request Headers](https://vercel.com/docs/headers/request-headers)는 전달 IP 헤더를 플랫폼에서 덮어쓴다고 명시한다. 다른 프록시/호스팅으로 옮기면 신뢰 경계 재검토가 필요하다. 공유 NAT 및 IPv6 주소 회전은 사용자별 인증 제한과 별개로 남는 한계다.

## 운영상 남은 한계

- fail-closed로 DB/풀 장애 때 정상 요청도 잠시 차단된다. 트랜잭션 대기 2초/실행 3초 제한을 두었으며 DB 왕복이 늘어난다. 실제 지연 비교는 배포 후 기록한다.
- 고정 창 경계에서 두 창의 예산이 근접해 사용될 수 있다. 이는 슬라이딩 창/전역 비용 예산이 아니며 기능별 공유 계정·네트워크 악용을 전부 막지는 않는다.
- 감사 쪽지의 기존 저장 트랜잭션 안에서 별도 제한 트랜잭션을 사용하므로 짧게 두 연결이 필요할 수 있다. 제한 카운터는 이후 콘텐츠 저장이 실패해도 성공한 입장 시도를 계산한다.
- 새 DB 스키마가 없으므로 이전 Preview 배포로 재지정해 코드 롤백할 수 있다. 새 카운터 행은 구버전이 무시하며 신고 증거·백업은 그대로 보존한다.
