## 발견 및 수정

1. **원본 삭제와 증거 복사의 경합**: 종전 코드는 신고 커밋 후 사진을 복사했다. 대상 게시글/메시지와 갤러리를 `FOR SHARE`로 읽고, 같은 신고 트랜잭션 안에서 복사 결과까지 저장한다. 갤러리 조회와 잠금은 한 SQL 문장으로 처리해 후속 조회가 잠금 없는 신규 행을 읽는 틈도 없앴다. Storage 요청은 사진별 전체 3초, DB 트랜잭션은 25초로 제한한다. 대기/데드락/DB 실패 시 신고 트랜잭션이 실패할 수 있으므로 클라이언트 재시도가 필요하다.
2. **복사 실패 복구**: 실패 시 캡처한 원본 경로만 비공개 스냅샷에 남긴다. `reports.view` 관리자가 처리 대기 신고에 대해 같은 사이트의 POST 요청으로 재시도할 수 있다. 현재 원본의 교체 사진을 다시 읽지 않는다. 원본이 이미 없어졌거나 이전 스냅샷에 재시도 경로가 없으면 복구할 수 없다. 완료된 사본은 덮어쓰지 않는다.
3. **권한·경로 검증**: 서명 시 저장된 경로의 신고 ID와 사진 인덱스가 요청한 신고/사진과 일치해야 한다. `reports.view`를 서비스와 API에서 확인하며 정지된 관리자에게는 권한이 없다. 공개 사용자 DTO·관리자 목록에는 스냅샷을 포함하지 않는다.
4. **캐시**: Storage 서명은 300초. 브라우저에 서명 URL을 전달하는 대신 관리자 인증 이미지 API가 스트리밍하며, `private, no-store` 및 CDN no-store 헤더를 반환한다. Next 이미지 최적화를 사용하지 않는다. 매 사진 요청에서 현재 권한과 채팅 사진 열람 기록을 다시 확인한다. 이미 사용자가 내려받거나 캡처한 바이트를 회수하는 기능은 아니다.
5. **열람 기록**: 채팅 스냅샷 본문도 반환 전에 기존 CHECK에 허용된 `chat_room` 기록을 남긴다. 사진은 서명 전에 `chat_image`를 기록한다. 기록 저장 실패 시 해당 비공개 내용을 반환하지 않는다. 페이지 렌더링과 이미지 요청은 각각 기록될 수 있다. 공개 게시글 증거 사진은 기존 채팅 전용 감사 테이블에 기록하지 않는다.
6. **보존 예외**: 탈퇴한 신고자의 신고 행을 지우는 경로에서도 피신고자의 정지·재가입 보류를 확인한다. 처리 후 365일 및 열람 기록 최소 보관기간, 진행 중 사안의 예외를 유지한다. 개인정보처리방침에는 신고 시점 사본과 열람 기록으로 인한 기존 보관 연장을 명시했다. 동의 버전은 변경하지 않았다.
7. **백업·복원**: 백업은 모든 버킷을 열거하므로 전용 백업 작업 트리의 기존 코드도 증거 버킷을 포함한다. 복원 검사에 채팅 이미지와 JSON 스냅샷의 증거 경로, 비공개 버킷 메타데이터, 실제 파일 SHA-256 대조를 추가했다. 전용 백업 작업 트리의 복원 검사 갱신은 검증된 커밋의 fast-forward로 별도 반영해야 한다.

## 롤백 원칙

- 앱은 검증된 이전 Production 배포로 되돌릴 수 있다. 이전 배포를 삭제하지 않는다.
- **앱 롤백 때 새 컬럼, 신고 스냅샷, `report-evidence` 버킷/객체를 삭제하지 않는다.** 기존 코드에서 보이지 않아도 보존한다. 과거 DB 전체 복원으로 신규 신고를 덮어쓰지도 않는다.
- 마이그레이션 파일 주석의 `DROP COLUMN` 예시는 데이터 수집 전 disposable 리허설에만 해당한다. 운영 롤백 명령으로 실행하지 않는다. 적용된 파일의 체크섬은 유지한다.
- 이전 앱의 retention은 새로운 증거를 이해하지 못하므로 장기 롤백은 별도 검토가 필요하다. 새 신고의 1년 보존 기한보다 먼저 전진 수정/복귀하고, 정리 정책을 확인한다.
- Storage는 DB와 원자적 커밋을 공유하지 않는다. DB 트랜잭션이 복사 후 실패하면 고아 사본이 남을 수 있다. 알려진 신고의 폴더 정리는 가능하지만 전역 고아 파일 관리는 릴리스 D 범위로 유지한다.
