# UTM 운영 표준 v1.0

기준일 2026-11-09. 이번 변경의 적용 대상은 Preview입니다. Production 반영은 별도 검증·배포가 필요합니다.

## 1. 값의 의미

| 파라미터 | 의미 | 경비실 포스터 기본값 |
| --- | --- | --- |
| `utm_source` | 유입 출처 | `poster_qr` |
| `utm_medium` | 홍보 매체 | `offline` |
| `utm_campaign` | 홍보 활동 | `poster_2026_11` |
| `utm_content` | 캠퍼스·건물·설치 유형·QR 용도 | `h_jonghap_guard_find` |

Campaign은 `poster_YYYY_MM`으로 발급 활동을 구분합니다. 장소가 바뀐다고 Campaign을 바꾸지 않습니다. 후속 홍보 활동은 새 Campaign과 등록부 행을 추가합니다. Content는 같은 장소·용도에 재사용할 수 있지만 다른 장소로 재배정하지 않습니다.

Content: `{campus}_{building}_{placement}_{purpose}`.

- 캠퍼스: 현재 확정된 곳은 `h`(인문캠퍼스)뿐입니다.
- 건물: 아래 확정 목록만 사용합니다. 건물 코드는 영문 소문자로 시작하는 영문·숫자 최대 12자입니다.
- 설치 유형: 이번 16개는 모두 `guard`입니다. 향후 같은 건물 내 여러 게시판은 승인된 위치별 `board01` 등으로 구분할 수 있으나 현재 게시판 설치 장소는 확정·발급하지 않았습니다.
- 용도: `find`(분실물 검색, `/search`), `reg`(습득물 등록, `/found/new`).
- 예: `h_jonghap_guard_find`, `h_jonghap_guard_reg`, `h_mcc_guard_find`, `h_mcc_guard_reg`.

모든 UTM 값은 영문 소문자·숫자·`_`·`-` 1~32자입니다. 기존 수집기와 동일하게 구분자를 제거한 뒤 7자리 이상 연속 숫자는 거부합니다. 이름·연락처·학번·자유 검색어·전체 URL을 값에 넣지 않습니다. 생성기는 공백 제거·소문자 정규화를 하며 CSV에는 정규화된 값을 저장합니다.

## 3. 발급·등록의 기준

원본은 [qr-registry.csv](qr-registry.csv), 건물 승인 목록은 [buildings.json](buildings.json)입니다. 관리자 생성기의 등록부 선택과 수집기의 승인 목록은 동일한 CSV로 생성한 `src/lib/metrics/qrRegistry.json`을 사용합니다.

```text
node scripts/operations/validate-qr-registry.mjs --write
npm run operations:validate
```

검증은 건물 코드·명칭, Content의 장소·용도 일치, source/medium/campaign, 목적지, URL, 중복 ID·조합, 날짜, 스냅샷 일치를 검사합니다. 생성기와 CSV 검증기는 같은 URL 조립 함수를 사용합니다. 빌드 전에 검증이 자동 실행되어 스냅샷 불일치 시 배포 빌드가 실패합니다.

Content가 있는 `poster_qr` 신규 QR은 등록부의 활성 항목 URL과 정확히 일치해야 생성됩니다. 미확정 건물이나 캠페인·용도에 맞지 않는 목적지는 오류로 차단합니다. 기존 Content 없는 링크는 호환성을 위해 계속 생성·접속할 수 있습니다.

등록부는 `qr_id`별로 한 행입니다. `ready`는 발급 준비, `installed`는 실제 설치 확인, `retired`는 회수/사용 종료입니다. 회수된 QR도 이미 배포된 링크의 분석을 위해 승인 목록에 유지합니다. 기존 URL·코드는 수정·삭제하지 말고 수정이 필요하면 새 식별자를 발급합니다. 설치 날짜·점검 날짜가 비어 있으면 미확인입니다.

## 4. 세션과 측정 범위

기존 정의 그대로 브라우저의 30분 비활동 또는 KST 날짜 변경으로 새 세션을 판단하고 첫 유입 화면에서만 UTM을 셉니다. 같은 세션의 새로고침·화면 이동·다른 QR 열기는 새 유입이 아닙니다. 관리자와 자동화 브라우저는 기존 정책대로 방문 통계에서 제외합니다. 운영자 테스트가 방문 세션으로 보이지 않는 것을 곧바로 고장으로 판단하지 않습니다.

로그인 전 직접 등록 링크는 서버에서 로그인·가입 화면으로 이동할 수 있습니다. UTM 네 값을 검증된 `callbackUrl`에 보존하고, 처음 렌더링된 로그인/동의 화면에서 그 값을 읽습니다. OAuth 후 화면 복귀와 UTM의 서버 수집·DB 반영은 **별도** 검증 항목입니다.

기존 집계는 변경하지 않습니다. 새 카운터는 다음과 같습니다.

- `visit.utm_content.<Content>`: Content가 있는 방문 세션.
- `visit.utm_pair.<Campaign>.<Content>`: 등록부에 존재하는 캠페인×Content 조합의 방문 세션.
- `meta.since.utm_content`: 이 환경에서 Content 측정 코드가 동작한 첫 일반 방문 세션의 날짜를 찾는 표식. Content 없는 방문도 표식을 기록합니다.

실제 저장 시 방문 카운터에는 기존 `audience_v3.` 접두사가 붙고 운영 통계는 기존 `OperationalMetricDaily` 뷰로 조회합니다. 원본 URL·IP·방문자 식별자는 새로 저장하지 않습니다.

Content 시작일은 환경마다 DB 표식의 최소 날짜로 정합니다. 첫날은 부분 측정, 그 이전은 **미측정**입니다. 이전 날짜의 빈 Content를 0이나 소급 추정치로 표시하지 않습니다. 기존 출처·캠페인의 수집 시작일과 새 Content 시작일은 별개입니다. Content 없는 기존 QR의 세션도 기존 집계에는 계속 포함됩니다.

## 5. 저장량과 장기 운영

기존 source/medium/campaign의 제한은 종류별·서버 인스턴스별·KST 일자별 **30개**입니다. 이미 본 값은 계속 세고 이후 새로운 값은 `etc`로 셉니다. 서버 재시작이나 다른 인스턴스에서 목록을 공유하지 않으므로 전역 30종 제한은 아닙니다. 이번에는 이 기존 의미를 바꾸지 않습니다.

새 Content에는 이 30종 제한을 복사하지 않습니다. 승인된 등록부 Content와 정확한 캠페인×Content 조합만 원래 값으로 셉니다. 미등록 Content는 `unregistered`, 미등록 조합은 `unregistered.unregistered`로 묶습니다. 유효하지 않은 값은 버립니다. 일반 생성기에서 문법상 유효한 값을 넣었다고 상세 집계되는 것은 아닙니다.

등록부는 회수 기록을 포함해 최대 1,024행입니다. Content 키 최대 1,024개, 조합 키 최대 1,024개, 미등록 범주 2개로 **새 상세 카운터 이름의 전역 종류 수를 최대 2,050개**로 제한합니다. 수집기는 등록부 외 입력으로 임의 키를 만들지 않으며 N×M 교차곱도 만들지 않습니다. 날짜별 행은 운영 기간에 따라 늘어나므로 이 제한이 DB 전체 행 수나 보유기간의 상한이라는 뜻은 아닙니다.

등록부가 1,024행에 가까워지면 기존 행을 지워 한도를 피하지 말고 용량·보유기간·검색 성능을 검토합니다. 이후 DB 기반 QR 정의·설치 이력·승인 워크플로로 옮길 수 있지만 이번 변경에는 QR 테이블이나 마이그레이션이 없습니다. 이전 링크의 정의와 카운터를 보존하는 별도 이전 계획이 필요합니다.

기존 캠페인이 30종 이후 `etc`로 묶여도 새 승인 조합 카운터는 원래 Campaign을 사용합니다. 따라서 새 상세 합계를 기존 캠페인 합계와 무조건 일대일 대조하지 않습니다. 같은 값의 UTM은 유입 분류이며 QR 소유자나 실제 설치 위치를 인증하는 수단이 아닙니다.

## 6. 기존 QR 호환성

`guard01`~`guard08` 형식은 신규 발급에 사용하지 않습니다. 이미 발급된 번호형 캠페인이나 Content 없는 링크는 그대로 열리고 기존 source/medium/campaign 통계도 유지합니다. 실제 설치와의 과거 대응은 확인 없이 추정하지 않으며 기존 통계를 새 건물 코드로 일괄 치환하지 않습니다.
