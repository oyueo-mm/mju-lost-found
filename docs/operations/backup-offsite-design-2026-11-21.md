# PC에 의존하지 않는 오프사이트 백업 설계 (Cloudflare R2 + GitHub Actions)

> 상태: **설계안(2026-11-21). 아무것도 만들거나 연결하지 않았다.** 5절의 승인 항목은 각각 별도 승인 대상이다. 가격·기능은 2026-11 기준 공개 정보이며, 도입 전에 다시 확인한다("확인 필요" 표시).

## 1. 배경
- 현재 자동 백업은 개인 노트북 한 대의 작업 스케줄러에서 돈다(`MJU Find daily backup`, worktree `C:\proj_claude\mju-find-backup-ops`).
- 2026-11-21에 WakeToRun을 켜서 절전 중 누락은 줄였다. 하지만 아래 경우에는 여전히 백업이 없다.
  - **AC 전원이 연결되지 않은 경우**: 이 PC의 전원 계획은 배터리에서 절전 해제 타이머가 꺼져 있다(`RTCWAKE` DC=0).
  - PC가 꺼져 있거나 최대 절전 상태인 경우
  - 로그오프 상태(작업이 "로그온한 경우에만" 실행)
- 암호화 백업 파일도 같은 PC 한 곳에만 있다. 3-2-1 원칙을 충족하지 못한다.

## 2. 목표
1. PC 상태와 무관하게 매일 1회 Production DB + Storage 3개 버킷을 백업한다.
2. 생성 즉시 복원 검증을 하고, 원격 사본의 무결성을 검증한다.
3. **암호화된 파일만** PC 밖(R2)에 보관한다. 평문은 CI 러너 안에만 잠시 존재한다.
4. 자격증명은 최소 권한으로 둔다. CI가 탈취돼도 과거 백업을 읽거나 지울 수 없게 한다.
5. 실패와 "아예 실행되지 않음"을 모두 감지한다.
6. 기존 로컬 백업과 병행하면서 단계적으로 전환한다.

## 3. 구조

```
GitHub Actions  (.github/workflows/offsite-backup.yml, schedule 19:00 UTC = 04:00 KST, workflow_dispatch)
 job: backup  (ubuntu-latest, timeout-minutes: 30, environment: offsite-backup)
  1. pg_dump --snapshot (PG 17 클라이언트, 전용 읽기 계정, BEGIN READ ONLY)  ── 기존 scripts/backup/backup.mjs 재사용
  2. Storage 3개 버킷 다운로드 + 목록·크기 대조                                ── 기존 코드 재사용
  3. 복원 검증: services: pgvector/pgvector:pg17 에 복원 → 테이블·행 수·이미지 참조 대조
                                                                         ── 기존 verify-restore.mjs / wsl-restore-check.sh SQL 재사용
  4. tar → age 암호화 (CI에는 수신자 공개키만 있음) → SHA-256 기록
  5. R2 업로드: daily/YYYY-MM-DD.tar.age (+ 일요일 weekly/, 1일 monthly/ 서버 측 복사)
  6. 업로드 객체를 다시 받아 SHA-256 대조 (복호화 없이 무결성만)
  7. 러너 정리 (평문 디렉터리 삭제; 러너는 일회용)
 실패 → GitHub 실패 알림 메일

운영자 PC (현행 유지, 병행 기간)
  - 매일 04:00 로컬 백업 (기존)
  - watchdog: 로컬 최신본 + R2 최신 객체 날짜 모두 26시간 이내인지 확인 (R2 읽기 전용 토큰)
  - 월 1회 복구 훈련: R2 최신본 다운로드 → age 개인키로 복호화 → WSL 복원 검증 (스크립트화)
```

### 저장소가 공개인 점에 대한 조치
- 백업 산출물을 Actions artifact나 cache에 남기지 않는다. 공개 저장소의 artifact는 로그인한 누구나 받을 수 있다.
- 로그에는 집계(행 수, 크기, 해시)만 출력한다. 행 데이터, 경로, 키, URL은 출력하지 않는다.
- 트리거는 `schedule`과 `workflow_dispatch`만 쓴다. fork PR에는 secret이 전달되지 않는다.
- secret은 GitHub **Environment**(`offsite-backup`)에 두고, 배포 브랜치를 `vercel` 하나로 제한한다.
- 서드파티 action은 커밋 SHA로 고정한다. `permissions: contents: read`만 준다.

## 4. 최소 권한 자격증명

| 자격증명 | 위치 | 권한 | 탈취 시 영향 |
|---|---|---|---|
| DB 전용 읽기 계정 `backup_reader` | Actions secret | 백업 대상 스키마 SELECT·USAGE만, 쓰기 없음, `default_transaction_read_only=on` | 데이터 읽기(현재 덤프와 같은 범위). 쓰기·삭제 불가 |
| Supabase Storage 읽기 | Actions secret | **확인 필요**: Supabase에 버킷 읽기 전용 키가 없으면 service key를 쓸 수밖에 없다. 대안은 `backup_reader`에 `storage.objects` SELECT를 주고 서명 URL을 서버에서 발급하지 않는 방식이며, 이는 검토가 필요하다 | service key라면 프로젝트 전체 권한. Environment 보호와 짧은 교체 주기로 완화 |
| R2 API 토큰(쓰기) | Actions secret | **해당 버킷 하나**, Object Read & Write | 새 객체 쓰기. 버킷 잠금(아래)으로 기존 객체 삭제·덮어쓰기 차단 |
| R2 API 토큰(읽기) | 운영자 PC | 해당 버킷, Object Read only | 암호문 읽기만 가능(복호화 키 없음) |
| age 수신자 **공개키** | Actions secret(비밀일 필요는 없음) | 암호화만 | 없음 |
| age **개인키** | 운영자 오프라인(비밀번호 관리자 + 인쇄본) | 복호화 | CI·R2에는 없음 |

- RLS 주의: RLS가 켜진 테이블 6개(정책 0개)는 소유자가 아니고 `BYPASSRLS`도 없는 역할로 덤프하면 **0행**이 된다. `backup_reader`에 `BYPASSRLS`를 줄 수 있는지(Supabase `postgres` 권한 범위)는 **Preview에서 먼저 확인**한다. 줄 수 없으면 해당 테이블에 SELECT 전용 RLS 정책을 추가하는 안을 비교한다. 이 경우 Production RLS 변경이므로 별도 승인이 필요하다.
- 새 함수와 테이블은 DB 권한 정책([db-privileges-step2-2026-11-21.md](db-privileges-step2-2026-11-21.md))대로 클라이언트 역할 권한을 회수한다. `backup_reader`는 default privileges로 새 테이블 SELECT를 상속받게 할지, 마이그레이션마다 GRANT할지 정한다(후자 권장, 백업 검증이 누락을 잡는다).

## 5. 보관·삭제 정책 (R2)
- 접두사별 수명 주기 규칙(R2 Object Lifecycle)

  | 접두사 | 보관 | 기존 로컬 GFS와 비교 |
  |---|---|---|
  | `daily/` | 15일 후 삭제 | 로컬 7일 |
  | `weekly/` | 9주 후 삭제 | 로컬 4주 |
  | `monthly/` | 13개월 후 삭제 | 로컬 3개월 |

- **삭제 방지**: R2 버킷 잠금(Bucket Lock) 규칙으로 각 접두사의 보관 기간 동안 삭제와 덮어쓰기를 막는다. 쓰기 토큰이 탈취돼도 과거 백업은 지워지지 않는다. 기능 범위와 요금제 조건은 **확인 필요**하다. 불가하면 버전 관리를 켜거나 별도 계정 버킷으로 주 1회 복사하는 대안을 쓴다.
- 객체 이름에 날짜만 쓰고 덮어쓰지 않는다. 같은 날 재실행은 `-2` 접미사로 남긴다.
- 백업 원본 삭제는 수명 주기 규칙만 한다. 사람이나 CI가 삭제하지 않는다.

## 6. 실패 감지
1. 작업 실패: GitHub 실패 알림 메일(cron을 마지막으로 수정한 사용자에게 간다). 실패 시 `issues: write` 권한으로 이슈를 여는 단계도 고려할 수 있지만, 공개 저장소에 운영 정보가 노출되므로 메일만 쓴다.
2. **실행 자체가 안 됨**: GitHub는 공개 저장소에서 **60일 동안 활동이 없으면 예약 워크플로를 자동으로 끈다**. 예약 실행이 지연되거나 건너뛰어지기도 한다. 그래서 독립 감시가 필요하다.
   - 1차: 운영자 PC watchdog이 R2 최신 `daily/` 객체가 26시간 이내인지 확인하고, 아니면 경고한다.
   - 2차(선택, 승인 필요): 외부 하트비트 서비스(예: healthchecks.io 무료)에 성공 시 ping을 보내고, 미수신 시 메일을 받는다. 새 외부 서비스이므로 별도 승인이 필요하다.
3. 복원 검증 실패는 작업 실패로 처리하고, 업로드하지 않는다.

## 7. 정기 복원 검증
- 매 실행: 러너 안에서 평문 덤프를 서비스 컨테이너에 복원·대조한다. 백업 파일 자체가 복원 가능한지 확인하는 단계다.
- 매 실행: 업로드한 암호문을 다시 받아 해시를 대조한다. 원격 사본이 온전한지 확인하는 단계다.
- 월 1회(운영자 PC, 스크립트): R2 최신본 → age 복호화 → WSL 복원 검증을 한다. **암호문 → 복호화 → 복원** 전체 경로와 개인키 보관 상태를 확인하는 단계다. 결과는 운영 문서에 기록한다.

## 8. 예상 용량과 운영비 (현재 규모 기준)
- 백업 1개: 약 25MB(DB 2.5MB + 사진 22MB, 2026-11-21 기준).
- 보관 개수: 일 15 + 주 9 + 월 13 = 약 37개 → **약 0.9GB**. 사진이 1년에 3배로 늘어도 약 3GB다.
- R2(2026-11 기준 공개 요금, 확인 필요): 저장 10GB/월, 쓰기(Class A) 100만 건/월, 읽기(Class B) 1,000만 건/월까지 무료이고 송신(egress) 요금이 없다. 이 사용량(쓰기 월 약 40건, 읽기 월 약 60건)은 **무료 범위 안 → 월 0원**이다. 초과 시 저장 GB당 월 약 $0.015다.
- GitHub Actions: 공개 저장소의 표준 러너는 무료다. 1회 약 5~8분 × 30 = 월 약 150~250분이다. 저장소를 비공개로 바꾸면 Free 계정 월 2,000분 안에 들어간다.
- 운영 시간: 월 1회 복구 훈련 약 10분, 키 교체 연 1회.
- 결론: **추가 비용 0원으로 시작 가능**하다. 단, R2 가입에 결제 수단 등록이 필요할 수 있다(확인 필요). 이는 "새 서비스 도입" 승인 대상이다.

## 9. 단계적 전환
| 단계 | 내용 | Production 영향 | 승인 |
|---|---|---|---|
| 0 | R2 계정·버킷(테스트·운영 2개), 수명 주기·잠금 규칙, age 키 쌍, GitHub Environment | 없음 | 새 서비스 가입 |
| 1 | 워크플로를 **Preview DB → 테스트 버킷**으로 1주 운영. 실패 주입(복원 실패, 업로드 실패, 토큰 만료) 확인 | 없음 | 일반 작업 범위 |
| 2 | Preview에서 `backup_reader`·RLS 덤프 검증(0행 방지) | 없음 | 일반 작업 범위 |
| 3 | Production `backup_reader` 생성 + secret 등록 → `workflow_dispatch` 1회 → PC에서 복호화·복원 교차 검증 | **DB 역할 추가(권한 변경)** | **별도 승인** |
| 4 | 예약 실행 4주 병행. 로컬 백업은 그대로 두고, watchdog은 둘 다 감시 | 읽기만 | 단계 3 승인에 포함 |
| 5 | 병행 결과 보고 → 로컬 백업 주기 조정 여부 결정(권장: 로컬은 주 1회 + 월 복구 훈련 유지) | 없음 | 별도 결정 |

- 롤백: 워크플로를 비활성화하고 secret과 R2 토큰을 폐기한다. `backup_reader`를 제거한다(별도 승인). R2의 기존 백업은 수명 주기에 따라 만료된다.
