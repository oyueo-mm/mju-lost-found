### 실제 TLS 사용 확인

배포된 함수의 소켓을 직접 볼 수는 없으므로, 다음 네 가지를 이어서 증명했다.

1. **Supabase 주소만 허용**: Production 런타임은 `accessPolicy.mjs`가 Supabase Production 주소만 허용한다. 다른 주소면 앱이 시작되지 않는다.
2. **TLS 설정이 반드시 붙음**: Supabase 주소에는 `pgPoolSettings`가 항상 `ssl: { ca: Supabase Root 2021, rejectUnauthorized: true }`를 붙인다. URL의 `sslmode` 같은 파라미터는 제거한다.
3. **어댑터가 설정을 그대로 씀**: 앱이 쓰는 `PrismaPg`는 이 설정으로 `pg.Pool`을 만든다. `scripts/operations/db-tls-adapter-check.mjs`로 확인했다.
   - 다른 CA를 넣으면 `TlsConnectionError`로 거부된다. 평문으로 다시 시도하지 않는다.
   - 앱 설정으로는 연결된다.
4. **조회 성공 = 검증된 TLS 연결**: 배포 후 DB를 조회하는 요청이 성공했다. 1~3에 따라 이 연결은 검증된 TLS 연결이다.

|---|---|---|---|

| 배포 기록(`deployments/record.mjs`) | 평문 | 검증된 TLS. Preview 배포에서 기록 성공 | 동작 |
| `pg_dump`(노트북 백업, 진단) | 미검증 TLS(libpq 기본 prefer) | `verify-full` + 고정 CA | 동작 |
| Prisma 마이그레이션 CLI | 미검증 TLS(prefer) | `sslmode=require` + 고정 CA + `sslaccept=strict` (`prisma7.config.ts`) | 동작 |
| 노트북 예약 백업(ops 작업 트리, `ops/backup`) | 스냅샷 평문 + 덤프 미검증 | 검증된 TLS(`0ff6a70`). Preview 실행 성공 | 동작 |

| 긴급 복원(RUNBOOK 수동 `psql`·`pg_restore`) | prefer | `PGSSLMODE=verify-full` 명시 | 동작 |
| 롤백(`vercel rollback`) | DB 연결 없음 | 같음 | 단, 대상 배포가 TLS여야 함(5절) |
| 로컬 전용(복원 검증, 로컬 회귀) | 로컬 | 로컬(변경 없음) | 영향 없음 |

## 5. Supabase SSL 강제 전 조건 (승인 시 확인)

1. **TLS 없는 경로가 없을 것**: 3절의 모든 경로가 TLS를 지원한다. 남은 미지원 경로는 없다.
2. **노트북 예약 백업이 새 코드로 성공할 것**: 2026-11-23 04:00 실행이 새 코드의 첫 Production 실행이다. 성공 기록을 확인한 뒤 진행한다.
3. **TLS 롤백 대상 확보**
   - 지금 롤백 대상 `dpl_FvfFRQpp…`는 TLS가 없다. SSL 강제 후 이 배포로 롤백하면 DB 연결이 모두 끊긴다.
   - 방법 A(권장): SSL 강제를 다음 Production 릴리스(예: 하드닝 P-5/A-3/A-4/A-5) 이후에 켠다. 그러면 롤백 대상이 `dpl_ZNj7p6cL…`(TLS)가 된다.
   - 방법 B: 강제 직전에 같은 앱 코드(`dede9ce` 이후)를 한 번 더 Production 배포해 TLS 배포 두 개를 확보한다(Production 배포라 승인 필요).
   - **TLS 롤백 가능 배포**: `dpl_ZNj7p6cLTuiKJESDE8ZYWiWf6znD` 및 이후 배포. `dpl_HbJbyTZF…`는 TLS지만 잘못된 클라이언트라 **사용 금지**.

4. **SSL 강제 자체를 되돌리는 법**: Supabase Dashboard → Database → SSL Configuration에서 강제를 끄면 즉시 원래대로 돌아간다. 데이터 변경은 없다.
