# UTM Content 신규 측정 구간 v1

2026-11-10 구현. UTM **명명 표준 v1.0과는 별개인 통계 측정 구간**입니다. URL·QR 등록부·utm_content 값·관리자 권한은 바꾸지 않습니다. 이번 작업은 Preview에만 배포하며 Production 활성화는 하지 않습니다.

## 구간별 저장·조회

| 구분 | MetricDaily 실제 키 | 처리 |
| --- | --- | --- |
| 기존 표식 | `meta.since.utm_content` | 보존, 날짜만 별도 표시. 실제 시작일·출처 미확인 |
| 기존 Content | `audience_v3.visit.utm_content.{content}` | 기존 기록 영역에 별도 표시 |
| 기존 조합 | `audience_v3.visit.utm_pair.{campaign}.{content}` | 기존 기록 영역에 별도 표시 |
| 신규 일별 최초 관측 | `meta.first.utm_content_v1` | day=KST 날짜, value=그날 최초 관측의 KST 초(0~86399) |
| 신규 Content | `audience_v3.visit.utm_content_v1.{content}` | 신규 구간만 집계 |
| 신규 조합 | `audience_v3.visit.utm_pair_v1.{campaign}.{content}` | 신규 구간만 집계 |

OperationalMetricDaily 뷰는 `audience_v3.`를 제거하므로 조회 코드에서는 `visit.utm_content_v1.*` 등으로 읽습니다. 기존 namespace에 새 카운터를 이중 기록하지 않습니다. 기존 값은 수정·복사·재계산하지 않습니다. 같은 날짜·같은 Content의 기존 100건과 신규 2건이 있어도 신규 보고서는 2건만 표시하고 기존 100건은 별도 영역·내보내기 표에 남깁니다.

## 활성화와 실제 시작일

1. Preview는 별도 Preview DB에서 같은 로직을 검증합니다. Preview 시작일이 Production에 전달되지 않습니다.
2. 후속 작업에서 검증된 코드를 Production에 배포합니다. 보호 장치와 DB 환경 검사는 유지합니다. 시작일을 SQL로 미리 삽입하거나 환경변수 날짜로 고정하지 않습니다.
3. Production에서는 고정 도메인 **mju-find.vercel.app**의 새 일반 세션만 신규 구간을 활성화합니다. 고유 후보 배포 URL이나 보조 별칭 방문은 신규 Content를 기록하지 않습니다. 기존 QR 16종과 생성 링크는 이미 이 고정 도메인을 사용하므로 URL 변경은 없습니다. 다른 도메인에서 신규 Content를 측정하려면 별도 검토가 필요합니다.
4. 봇·관리자·수집 거부 방문, 기존 세션의 단순 이동·새로고침은 최초 관측을 만들지 않습니다. UTM이 없는 새 일반 세션도 관측 표식은 기록합니다. 따라서 관측된 세션 중 Content 태그가 0개인 경우와 미측정을 구분할 수 있습니다.
5. 새 코드 이전에 시작된 세션을 소급 귀속하지 않습니다. 실제 첫 신규 세션은 배포보다 늦을 수 있습니다. 화면에는 **배포 시각이 아닌 저장에 성공한 최초 일반 세션의 서버 관측 시각**을 KST 초 단위로 표시합니다. DB 커밋 시각과도 다릅니다.

## 원자성·경쟁·실패

일별 최초 관측은 서버 메모리에서 최소 초를 모으고 기존 flush 트랜잭션에 함께 저장합니다. 카운터와 같은 트랜잭션이므로 표식만 성공하고 카운터가 실패하는 상태를 만들지 않습니다. 여러 인스턴스의 같은 날짜 기록은 `LEAST`로 가장 이른 초를 보존하며 타임스탬프를 덧셈하지 않습니다. 정수 초는 기존 Int 컬럼에 들어가므로 DB 스키마 변경이 없습니다.

실패한 flush는 카운터와 최소 관측값을 함께 되돌려 재시도합니다. 재시도 중 새 관측이 들어와도 최소값을 보존합니다. 프로세스 종료로 미저장 관측이 유실되면 그 관측을 측정 시작으로 선언하지 않습니다. 날짜 사이의 전역 최초 관측은 새 표식의 가장 이른 day·second로 결정합니다. 이전 표식은 이 계산에 참여하지 않습니다.

## 일별 측정 상태와 롤백

- 선택일에 새 관측 표식이 없으면 **미측정(null)**입니다. 시작일 이전, 롤백 공백, 미래 날짜를 자동으로 0건 처리하지 않습니다.
- 표식이 있는 날은 모두 **부분 측정**입니다. 시작일뿐 아니라 이후 날짜도 하루 전체 가동을 입증할 heartbeat가 없으므로 완전 측정으로 추정하지 않습니다. 같은 날 롤백 공백이 있어도 전체 24시간을 측정했다고 표시하지 않습니다.
- 표식이 있는 날의 0건은 **관측된 일반 세션 중 Content 태그가 없었다**는 뜻입니다. 하루 전체 방문이 0건이라는 뜻이 아닙니다.
- 표식 없이 신규 카운터만 있거나 최초 관측 조회가 실패하면 신규 측정 합계에 포함하지 않습니다. 기존 기록은 별도로 계속 보입니다.
- 롤백은 앱 배포만 되돌립니다. 새 표식·카운터를 삭제하거나 초기화하지 않습니다. 현재 Production 롤백 대상 `3bf44fc`에는 Content 기록 코드가 없어 새 구간이 중단됩니다.
- 같은 구간을 재배포하면 새 키로 재개하고 과거 키와 합산하지 않습니다. 최초 관측은 유지되며 일별 공백은 미측정으로 남습니다. 같은 날짜 안의 공백 길이는 일별 자료만으로 복원할 수 없으므로 부분 측정을 유지합니다.
- 향후 정의가 달라지면 기존 v1 키를 재사용하지 않고 새로운 측정 구간을 설계합니다.

## 호환성과 저장량

Source·Medium·Campaign과 기존 방문 세션 집계는 기존 방식·시작일을 유지합니다. 동일 세션 첫 유입, 관리자·봇·수집 거부 제외, 등록부 allowlist와 unregistered 묶음, 기존 30종 제한도 유지합니다. 신규 Content가 기존 캠페인 총합과 측정 기간이 다를 수 있으므로 서로 같은 기간의 합계로 해석하지 않습니다.

추가 저장은 새 namespace의 유한한 Content·조합 키와 날짜당 최초 관측 1행입니다. 기존 등록부 최대 1,024개 기준 Content/조합 상세 키 최대 2,050종 제한은 변하지 않습니다. 방문마다 별도 DB 질의를 추가하지 않고 기존 배치당 최소값 upsert 문장 1개를 추가합니다. DB 마이그레이션·의존성·환경변수 변경은 없습니다.

## Production 재개 전 점검

Production 기존 기록·새 키 부재를 읽기 전용으로 재확인하고, Preview의 실제 신규 수집·기존 행 보존·화면/내보내기 분리를 확인합니다. 배포 승인 후 고정 도메인 연결과 버전 API를 검증합니다. 관리자 검증만으로는 신규 시작일이 생기지 않는 것이 정상입니다. 실제 정상 트래픽을 확인하며 운영 데이터에 합성 방문을 만들거나 표식을 수동 보충하지 않습니다. 실제 Google OAuth·휴대전화 스캔은 별도 검증 여부를 명시합니다.

이 구간 분리는 [기존 사건](statistics-integrity-2026-11-10.md)의 정확한 원인·증가량을 복원하거나 과거 값을 정상/잘못된 값으로 확정하지 않습니다.
